# SCM Node Affinity and Load Balancing

The purpose of this doc is to explain what SCM node affinity is, the need for some form of SCM load balancing in a 
clustered/multi-node environment and the implementation of that.

Draft date:  29 Dec 2023

## Background

Some SCM providers, Github in particular, prohibit simultaneous API requests for the same SCM user.  At the same time
a lot of SCM work is generated by policy evaluations and easy onboarding as well as the SCM background processes
like default branch monitoring, pull request polling and pull request monitoring and there is a need to parallelize
this work as much as possible.  All of these activities involve one or more SCM API requests and customers typically
have a finite number of SCM API tokens with which these requests are made.  Tokens are associated with users and it's
the user, not the token itself, on which Github bases its API rate/abuse limitations.

Initial SCM support for IQ clustering 3+ years ago involved a simple mechanism by which only one node in a cluster
was permitted to perform SCM operations, thus ensuring that requests for the same user could be sequenced and would
thus not overlap.  It was on the team's radar to implement something more sophisticated but the team was disbanded
as part of the annual re-org and that work was never picked up.

Fast-forward to today with multiple customers leveraging our new multi-node Lifecycle SaaS environment and the need
for multiple nodes to participate in SCM operations and share the SCM workload becomes apparent.

## Node affinity

Theoretically, in the SaaS environment any node should be able to process any request, no matter if those requests
originate from Quartz, background processes, HTTP or some other source.  If we took this approach with SCM
we'd have to implement some global form of locking such that whenever one node was processing an SCM event for a
given user no other node would be permitted to process some other event on behalf of that user at the same time.

On the surface this seems plausible but there are a couple of major flaws with this approach.  

First, there would be a significant reduction in SCM throughput as we wouldn't be able to process events for the same 
user in parallel.  Some SCM events, like commit status, are very simple and involve only a single API request to the 
SCM system.  These types of events would be easy to distribute/coordinate across nodes.  However, most of our SCM
operations are complex and involve many API requests/interactions with the SCM system.  Take pull request commenting
for example.  A PR comment involves first deleting any previous comments we've made on a PR via individual API requests
for each line comment and the overall comment.  Then we lay down the new comments, again via individual API requests
and along the way we record in our database what we've done.  It would be neither feasible nor efficient to split
this operation across nodes.  In addition, while one SCM operation is performing background work another SCM
operation/event can interact with the SCM API - thus the parallelization of SCM events.

Secondly, the current system is designed to maximize throughput and efficiency of SCM operations.  We allow multiple
events of various types to be processed in parallel with SCM API requests for the same user funnelling thru
a single locking mechanism.  It would be impractical to redesign the SCM integration to make the granularity of
operations the individual API requests themselves.  And, as mentioned in the first point, it would be terribly
inefficient to do so.

Thus, the concept of/requirement for node affinity:  SCM operations on behalf of the same SCM user are performed
by the same node for as long as that node is processing SCM events for that user.

## Load Balancing

The current implementation whereby all SCM events are processed by the same node is a form of node affinity and while
it might be ok for a single customer it's not the ideal solution for multiple customers sharing our SaaS environment.

We put some brain CPU cycles to this several years ago and laid some of the groundwork by adding the SCM user to the
SCM event table in preparation for distributing the SCM workload across nodes in the cluster, but again, we never
got the opportunity to take it any further.

Recently, as part of the SCM work for MTIQ I was able to spend some time looking at this problem again.  I devised a 
mechanism to 'partition' the SCM work and distribute it across multiple nodes.  In fact, I came up with multiple 
approaches and each time I went to create a POC for it I thought "this is too complex - how can I make it simpler?"

### Generalizing

Before I get into the details I want to point out that although I was solving an SCM specific problem I realized
that the need to partition workloads across nodes in a cluster might be something that would apply to other scenarios.
So, the core implementation is more general with a specific implementation for SCM.  More specifically, the
SelfThrottlingLoadBalancer provides a generic implementation with the SourceControlLoadBalancer providing the 
SCM-specific implementation.

### Partition Key

SCM workloads are partitioned by tenant and SCM user.  These two pieces of information are hashed together to form
a unique partition key, which will be described in more detail shortly.

### Perpetual Locks

The usage of the perpetual locks has been expanded for the SCM load balancer.  A 'category' was added so that other
types of workloads could leverage load balancing (via a custom SelfThrottlingLoadBalancer implementation).

A new 'heartbeat' lock was added.  Each running IQ instance will generate/maintain a heartbeat lock as a way to 
advertise itself to all other running instances, and vice versa.

Partition locks replace what was previously known as the instance lock (one lock to control which IQ instance could
process SCM events), and the InstanceManager was replaced by the load balancer.  So, we've gone from one instance lock
to many partition locks.

### The solution

After several attempts I believe I arrived at a pretty simple solution to the problem.  It's more along the lines of 
a reservation-type system where instances ask the load balancer "can I do this?" as opposed to a typical load
balancer that sits external to the instances and routes traffic.

- running instances create heartbeat locks (perpetual locks identified by a UUID generated by each instance)
- running instances obtain partition locks as needed (perpetual locks identified by the partition key)
- the system tries to evenly distribute partitions across instances
    - each instance periodically performs a 'partition analysis'
        - obtain all the 'source-control' perpetual locks (heartbeat and partition)
        - divide the number of partition locks by the heartbeat locks to determine the ideal/fair load for each instance
        - an instance that is 'overloaded' will 'forget' some of its partitions until the ideal partition count is reached
          - the locks associated with the forgotten partitions will eventually expire and those partitions will then become available to other instances
    - each SCM operation supplies the tenant and SCM user and asks the load balancer if it can process that work
      - the load balancer tries to get a lock for the associated partition and either succeeds or fails
        - success means that this instance can process the SCM operation
        - failure means either (a) another instance currently owns that partition lock or (b) this instance is already at the ideal partition count and can't take on another partition

The simplicity of this solution relies on the 'self-throttling' nature of it, and thus the name for the class.  If an
instance determines that it is servicing too many partitions it 'self-throttles' and makes some of its partitions available for
other instances.  At that point it's first-come, first-served.

Important note:  An instance giving up its partitions doesn't mean it gives up its locks.  There may still be SCM
operations in flight using those partitions.  So, those partition locks will either be allowed to expire so they can be picked up by other
instances or there are cases where the locks can be proactively released.

### Key classes

These classes were added to a new 'scale' package in the insight-brain-service module:

#### HeartbeatPartitionManager

The HeartbeatPartitionManager is solely responsible for maintaining the heartbeat lock for a given instance.  When
an instance is taken down/offline the heartbeat lock won't get renewed and the lock will expire, at which point the
instance no longer exists from the perspective of the other instances.

#### PartitionHelper

The PartitionHelper performs the partition analysis to determine whether or not the given instance is at/above/below
the ideal partition count and makes the determination whether a given instance can 'try' to get a given partition lock.

#### SelfThrottlingLoadBalancer

The SelfThrottlingLoadBalancer is a base class that provides all the core functionality for load balancing and
leverages the heartbeat partition manager, partition helper and the existing perpetual lock manager.  It uses
partition keys, but has no knowledge of what those keys represent or how they were created.  It answers a basic
question: 
```boolean canUsePartition(String partitionKey)```

The following scm-specific load balancer was added to the `sourcecontrol` package:

#### SourceControlLoadBalancer

This class provides basic load balancer configuration specific to SCM, formulates the partition keys based on the
tenant and SCM user, and answers more specific questions related to SCM, such as:

```java
  public boolean canPollForPullRequests(String scmUsername)

  public boolean reserveEvent(SourceControlEvent sourceControlEvent) 

  public List<SourceControlEvent> acquireEventsToProcess()
```

```acquireEventsToProcess()``` does a few things:
- unassigns events where the associated parition lock has expired
- obtains a list of unassigned events from the source_control_event table
- returns only those events for which it can get a partition lock
